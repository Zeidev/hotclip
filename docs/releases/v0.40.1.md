# HotClip v0.40.1 — 模糊填边终于有了开关
## 问题在哪
上一版把「模糊填边」做进了引擎(整帧落在一份模糊压暗的自己上,而不是把横屏素材的两侧
裁掉),但值只能由 `CutOptions` / `ExportRenderOptions` 给:**渲染面板上没有任何开关**,
界面里也没有任何地方能让这个值变成 `blur`。能力在引擎里,用户开不出来——横屏素材进竖屏
依然只有中心裁切一条路。
## 界面开关(`ExportPanel.tsx` / `export-options.ts` / `render-prefs-store.ts` / `api-types.ts` / `main/index.ts` / `scheme-store.ts`)
- 「竖屏 9:16」开关**下面**新增一行分段选择:**裁剪 | 模糊**。关掉竖屏时整行置灰
  (横屏出口本来就不走这条路径)。
- **出厂默认裁剪**:老用户升级后画面一个像素都不变;老偏好里没有这个字段、或存了认不出的
  值,一律回落裁剪。
- 值一路透传:面板 → `RenderPrefs.fillMode` → `buildRenderToggles` → IPC
  `ExportOptions.fillMode` → 主进程 `normalizeFillMode`(IPC 收上来的是 unknown,只认
  `crop` / `blur`,别的当「没指定」)→ 引擎。CLI / MCP 走同一份契约。
- `fillMode` 进**方案快照**白名单:存方案/切方案不会把这个选择抹掉。
- `FillMode` 的类型唯一来源仍是 `core/fill.ts`,`shared/api-types.ts` 只做转出,免得两边
  各长一份枚举悄悄漂移(纯类型引用,编译后不留运行时依赖)。
- 三语文案(en / tr / zh),hint 里写明:有跟拍目标或开了自动运镜时不生效(构图已经有人
  主张),横屏版不受影响。
## 已知缺口
- **没有真的导出一条模糊填边的成片看画面**。接线由单测钉住(面板选择 → `ExportOptions` →
  画面滤镜链三跳,含「开关死了」这一类死值检测),滤镜链的像素级证据在 v0.40.0 那版的
  `.seamtmp/probe-fill.ts` 里(不提交)。
- 本机完整套件仍有 1 项失败:`cover-quality.integration`(`candidatesRejected 1 < 2`),
  它依赖的 `cover-quality.ts` / `cover.ts` / `binaries.ts` / `runFfmpeg` 本版均未改动,
  判定为本机 FFmpeg 环境问题(与 v0.40.0 同一项)。
## 验证
两套 tsconfig(`node` / `web`)类型检查通过;`npx vitest run` 本机 **1,766 项通过、1 项
跳过、1 项失败**(即上面的环境项)。新增 `src/renderer/src/components/workbench/__tests__/export-options.test.ts`:
出厂默认是裁剪且画面一个像素不变、选了模糊后滤镜链换成模糊填边(居中裁切那步消失)、
横屏出口不受影响、`normalizeFillMode` 对乱值一律回落、方案快照带上这个开关。
## English
**Why**: v0.40.0 put the blurred fill in the engine — the whole frame sits on a
blurred, dimmed copy of itself instead of having the sides of a landscape source
cut away — but the value could only come from `CutOptions` /
`ExportRenderOptions`: there was no switch in the render panel and nothing in the
UI could ever produce `blur`. The capability was in the engine and the user could
not turn it on, so a landscape source going 9:16 still had exactly one path,
centre crop.
**Fixes**: a segmented control (**Crop | Blur**) sits directly under the vertical
9:16 switch and greys out when vertical is off (the landscape export never took
this path). The default stays **crop**, so an upgrade changes no one's picture
byte for byte, and a stored preference without the field — or with a value that
is not recognised — falls back to crop. The value travels panel → `RenderPrefs`
→ `buildRenderToggles` → IPC `ExportOptions.fillMode` → main's `normalizeFillMode`
(the IPC value is unknown; only `crop`/`blur` are accepted and anything else
means "not specified") → engine, with CLI and MCP on the same contract, and
`fillMode` joins the scheme snapshot whitelist so switching schemes no longer
drops the choice. `FillMode` still has exactly one definition (`core/fill.ts`);
`shared/api-types.ts` only re-exports it, so the two cannot drift apart. Labels
and hints ship in English, Turkish and Chinese, and the hint says the fill is
skipped when face tracking or auto-zoom already owns the framing, and never
applies to the landscape export.
**Known gaps**: no real export of a blurred-fill clip was watched; the wiring is
pinned by unit tests (panel choice → export option → picture filter chain, three
hops, including the "dead switch" case where the value arrives but the engine
ignores it), and the pixel-level evidence for the filter chain itself is the
`.seamtmp/probe-fill.ts` probe from v0.40.0 (not committed). The one local
failure, `cover-quality.integration` (`candidatesRejected 1 < 2`), is a local
FFmpeg environment issue whose dependencies are untouched here.
**Validation**: both tsconfigs typecheck clean; `npx vitest run` reports 1,766
passing, 1 skipped and the environment failure above, including the new
`src/renderer/src/components/workbench/__tests__/export-options.test.ts`.
